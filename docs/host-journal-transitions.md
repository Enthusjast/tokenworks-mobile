# Host 日志状态转换的事务边界

`PersistentCommandJournal` 的启动、完成和失败转换均先取得 SQLite `BEGIN IMMEDIATE` 写锁，
再读取当前 owner、摘要、状态和错误类别，判断转换、加密结果并更新。同一事务内的幂等返回
保留原结果；不能用等待写锁前读到的状态覆盖另一进程已经提交的事实。

旧实现先读状态，再开始事务。WAL 模式允许它在另一 writer 尚未提交时读到此前的合法状态；
随后即使 BEGIN 等待结束，也会直接执行基于旧状态的 UPDATE。两个实际 Node 进程稳定复现了：

- `outcome_unknown` 被迟到完成改成 `agent_queued`，并清除了待对账正文。
- `settled` 被迟到失败改成 `outcome_unknown`。
- 已完成结果被另一条相同完成调用的结果替换。
- `rejected` 被迟到启动改成 `dispatching`，正文已被原拒绝清除，重开时因此报完整性错误。

修复后，等待结束的调用重新检查已提交状态。迟到完成、迟到失败和迟到启动保留原事实并返回
`journal.invalid_transition`；相同目标状态的重复完成成功返回，保留最先提交的加密结果。

`admit` 和 `noteResult` 原来已经在事务内检查。此次没有改变状态图、请求摘要、owner 绑定、
加密格式、数据库版本、协议或未知结果的处理规则。修复不提供跨进程原生执行所有权，
也不把允许多个 SQLite 连接等同于允许多个 DSH writer；宿主仍须维护会话与运行实例所有权。
同一路径上的各进程应使用修复后的实现，旧 writer 不受新代码约束。已有不可解读的日志仍按原完整性检查失败，
不会因本次修复自动删除、重置或推断未知操作的执行结果。

状态转换及相同结果重试现在都会产生实际事务尝试，沿用[日志事务观测](host-journal-observations.md)。
这些样本可以只有校验/读取，不代表新增命令、状态变化或再次执行。

定向回归使用两个真实 Node/SQLite 进程，先让 writer 完成 UPDATE、暂停在 COMMIT 前，
再让 contender 到达 BEGIN，最后释放第一次提交。控制钩子只同步边界，不替代 SQL 或手工改写行。
测试核对重开后的终态、原错误/结果、未知正文和相同 ID 去重，不修改系统时钟或延长生产锁期限。
相关的命令日志、事务观测和已安装 DSH CLI 用例另作集中验证；未运行全量或 Windows 测试。

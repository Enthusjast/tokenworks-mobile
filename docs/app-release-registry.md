# APK 发行身份持久登记

Go 服务启用 `REMOTE_APP_RELEASES_FILE` 后，在打开业务、私有 Relay 或指标监听器之前，
将整份合法目录的 APK 身份与 PostgreSQL 核对。迁移 `050_app_release_artifacts` 保存不可变登记，
防止进程重启或不同节点把同一发行标识解释成另一份 APK。它不上传、签名或发布 APK，也不修改 Android APP。

## 登记的事实

每个 `release_id` 在整个数据库内唯一；`package_name + version_code` 也唯一。
两者必须始终指向同一组字段：

- 发行 UUID、包名、版本号与版本名称。
- 文件 SHA-256、字节数和签名证书 SHA-256。
- 最低／最高协议版本和最低 Android API。

以上字段使用 `dsh-app-release-artifact/v1` 域和 RFC 8785 生成 SHA-256 指纹，
登记保存完整字段及指纹。兼容范围也是发行物的已核对描述，不能通过重启静默改写；
发现登记错误时需修正发行流程并使用新的版本号及 UUID，不提供覆盖或删除历史的 API。
登记不解析 APK 字节，也不能证明配置与实际 APK 或已安装签名一致；发行端仍须核对制品，
客户端下载后仍须执行独立的哈希、包名、平台签名和升级兼容检查。

下载 URL、发行说明、目标组织、灰度比例及支持的客户端版本窗口属于当前分发策略，
可在受保护配置中修改，不改变已登记身份；应用迁移 051 后须先显式变更[共享发行策略](app-release-policy.md)，再加载同一配置重启。来源仍受原有 HTTPS allowlist 和客户端独立信任限制。
比例为零的 publication 也会登记；从目录移除或停用整个发行功能不会释放 UUID／版本号。
之后恢复相同制品可以再次使用原登记；相同版本换 UUID、相同 UUID 换包名／版本或变更制品都会拒绝启动。

## 事务、审计和恢复

服务在当前 ready 数据库代次下对整份目录执行一个事务。短暂的登记表锁协调并发节点，
随后核对两种唯一标识和完整不可变字段；任何一项冲突或数据库／审计失败，整批回滚，
目录不交给 HTTP handler，服务不开放监听器。错误只报告固定配置类别，不回显数据库详情、
下载地址或发行说明。不能把启动失败当作自动停用更新目录。

首次成功插入每个制品时，数据库触发器在同一事务写一次 `app.release.register` 审计，
只含发行 UUID、包名、版本号、身份指纹和登记代次。重启或提交结果丢失后重试相同目录，
只核对原记录，不重复写审计。登记成功不表示进程随后就绪、目录已经被查询或客户端已经安装。修改、删除和 truncate 被触发器拒绝；已有记录时 down 迁移也拒绝，
回退应保留该表并采用前向修复。旧 `app_releases` 占位表不参与选择，也不会自动成为可信登记来源。

恢复隔离期间不能登记。正常隔离／释放流程切换数据库代次后，原制品身份继续保留，不能借新代次
复用旧 UUID／版本号。恢复旧备份仍可能丢失备份之后的登记，因此需要与部署方独立保存的当前可信发行
清单核对；本功能不提供外部防回滚账本或丢失记录恢复能力。

## 部署顺序和边界

1. 核对已发行制品与可信配置，备份当前登记与审计；首次上线只能固定这次提供的可信目录，
   不能自动发现此前从未登记且已撤回的制品。
2. 先应用迁移 050 与 051，再部署新服务。每个提供发行查询的节点均需升级；旧二进制不会核对新登记，
   不能把混合版本部署写成已经统一约束。
3. 新进程只有在整份目录核对成功后才开始监听。节点启动失败应核对可信制品和既有登记，
   不能删表、改历史或换 UUID 来让同一版本通过。

登记只固定制品身份。[共享策略核对](app-release-policy.md)另行约束灰度、撤回、组织和版本窗口；
各节点使用的配置仍须受控分发和重启，没有增加自动配置分发、强制升级或下载托管。

## 本地验证

集中定向用例覆盖发布策略变更、撤回／重启幂等、双标识冲突、兼容元数据变更、整批冲突回滚、
审计被抑制时回滚、并发节点只能登记一个冲突身份、数据库恢复隔离／释放和禁止破坏性回退。
生产二进制测试使用本地 PostgreSQL 与公开配置夹具：正常配置就绪，变更文件哈希的重启在监听前
失败，保留原制品但调整灰度可重新就绪，最终登记和首次审计均只有一份。
没有下载或安装 APK，也没有使用学校身份、Android、真机、Windows、Wine、厂商通道或大负载。

# 主机登记的组织管理员审批

组织可以在现有受保护、带数据库 epoch 和 revision CAS 的身份目录快照中，
为 organization 设置 `enrollment_admin_approval_required: true`。
通过原有 `remote identities apply` 流程同步，不从手机或 Host 请求读取组织策略。
新组织省略此字段时默认为 false；对已有组织省略或使用 null 会保留当前策略，
旧版快照不会关闭已开启的审批。显式 false 仅影响之后创建的申请。

先应用 migration `047_enrollment_admin_approval`，再部署 Go 和 Host 更新后开启策略。
数据库在创建申请时记录审批要求；开启策略也会收紧该组织所有 pending / user_confirmed 申请。
已批准实例保持原有授权和撤权流程，不追溯认证历史安装。
已经要求审批的申请不会因后续策略放宽而自动放行，需完成管理员审批或到期后重新登记。
迁移拒绝删除仍被组织策略或申请记录使用的审批字段。

## 独立确认与激活

手机确认、Host 本机确认的代码、账号和密钥检查保持原有要求。
要求管理员审批时，两者均确认后仍为 `state=user_confirmed`，
`user_confirmed=true`、`host_confirmed=true`，不创建初始 owner grant，也不提供实例连接权限。
只有当前组织管理员通过独立接口批准，才在同一事务中激活 Host、批准申请、
创建安装所有者与手机确认用户的初始授权，并写入 audit / control outbox。
管理员也可以是已有参与者，但其手机或本机确认不会自动算作管理员批准。
管理员未批准的申请按原五分钟期限到期。

数据库约束和触发器也执行审批门槛。旧节点忽略新字段并尝试直接批准时会失败，
不能绕过门槛；它们也无法清除已记录的审批要求。
组织策略变更与激活通过组织行锁串行化；锁竞争或串行化失败可能返回暂时不可用，
需要重新读取状态和审核信息，不能把失败当作未提交。

## 管理员 API

两个接口均要求原有 phone OAuth client、有效 DPoP、当前注册设备，
以及数据库中当前有效的组织 admin 成员关系。Host client、普通成员、
其他组织的管理员、已撤销设备或错误证明密钥均不能使用；ID 和审核摘要本身不授予权限。

| 方法 | 路径 | 含义 |
| --- | --- | --- |
| GET | `/v1/enrollments/{id}/admin-review` | 返回管理员专用审核信息及服务端计算的 `review_sha256`；不接受 query 或 body。 |
| POST | `/v1/enrollments/{id}/admin-approve` | JSON body 仅含规范小写十六进制 `review_sha256`。 |

管理员通过可信组织目录核对审核中的安装所有者、手机确认用户、主机别名、profile、
安装公钥指纹和工作区范围，再把原审核摘要提交给批准接口。
审核不返回配对码或私钥；返回的 issuer / subject 是原有验证身份键，应作为不可信文本展示。
此批提供服务端 API，没有添加 Android 管理员界面或学校后台集成。

摘要是服务端的版本化、不透明复核凭据，客户端不自行计算。
它绑定申请、安装、runtime、原请求摘要、有效期、双方身份与当前资格、
手机设备/密钥版本、手机及本机确认时间和工作区映射。
批准时重新构造并比较同一审核摘要，同时重新检查双方成员资格、设备版本、
资源撤销状态和管理员权限。手机换设备/密钥后重新确认，会清除旧本机确认，
必须重新本机确认和管理员审核。旧摘要不能批准这次新的确认。

审计记录管理员的用户/设备来源、设备密钥版本、审核摘要和批准时间；
成功重试不会重复创建 grant、审计或 outbox。
丢失批准响应时，使用同一管理员账号和原摘要重试，或读取 `admin-review` 中的
`state` 与 `approved_review_sha256` 对账。历史重试仍需要当前管理员和设备权限，
不会重新创建后来撤销的 grant，也不会把其他管理员的决定据为己有。
申请期限在密钥/成员、grant、audit 和 outbox 等等待之后再次检查；过期会回滚整个激活事务。

## Host 与现有客户端兼容

现有 participant / host-review / confirmation 的 JSON 字段和 state 词表保持不变。
Android 无需协议解析变更即可继续查询最终 approved 状态；本批没有调整其等待文案。
Host 本机确认得到双方均确认的 user_confirmed 后，只轮询原申请，等待最终批准。
等待期间不重发本机确认，也不新建申请；取消、断线或进程重启后，
可用原有受保护的 recovery / binding 记录显式恢复这一只读等待阶段。
身份改变、设备失效、本机确认被清除或申请到期都会停止等待。
只有服务端确认 approved 后，binding 才能打开并继续既有凭据流程。

## 验证范围

定向 PostgreSQL 夹具覆盖策略收紧/放宽、旧快照兼容、数据库阻止旧节点激活、
独立管理员批准、当前角色/设备证明、跨组织隔离、无提前凭据/连接/授权、
确认密钥轮换与旧审核摘要、批准重试和审批等待过期后的事务回滚。
HTTP 夹具覆盖实际 JWT / DPoP 与严格请求体；Host 夹具覆盖等待、身份变化和受保护原申请的恢复。
这些不构成学校生产管理员门户、真实身份配置或目标负载验收。

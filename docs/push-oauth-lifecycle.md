# FCM 凭据刷新与任务取消

FCM service-account token source 在内存中复用尚有一分钟余量的 Google access token。
缓存同时核对墙钟和单调期限。刷新时只有一条 provider 请求；状态互斥锁不跨 RSA 签名、
HTTP 请求、响应体读取或清理持有。

发起者与其他等待者分别按自己的上下文等待。某个等待者到期或取消会立即返回固定的
`push: unavailable`，不会取消其他调用者的有效刷新。发起者拥有共享请求的生命周期，
其取消会取消共享刷新；共享请求还有独立的十秒总期限，不会脱离原通知任务或服务退出上下文继续申请凭据。

同批等待者共同观察一次刷新成功或失败。失败不会让它们依次自动申请新 token；
下一次独立调用才可以重新尝试，通知任务仍由原有持久队列退避和重新授权控制。
请求取消、超时或失效后，如果底层 transport 尚未结束，刷新槽继续被占用，
不启动并行的替代请求；迟到响应不能重新发布凭据。

FCM 的 401 响应只失效与当前缓存相同的 token，迟到的旧 token 拒绝不会清除不同的新 token。
失效匹配缓存时增加本地代次，并取消当时的刷新；该刷新即使返回有效格式的 token 也不能跨代次写回缓存。
失效操作只获取短状态锁，不等待 provider 网络结束。它不改变用户授权或通知的持久发送结果。

凭据返回后，sender 仍重新检查通知、设备、grant 和租约，再调用 FCM。
缓存或刷新成功不代表有权发送，也不表示 provider 已接受通知或手机已展示。
token、service-account assertion、响应正文和原始异常不进入日志或指标标签。

定向 race 用例使用本地 TLS OAuth 对端及忽略取消的受控 transport，覆盖等待者取消、
共享失败、后续恢复、发起者取消、刷新期间失效、迟到响应、槽所有权与缓存返回前取消。
既有用例继续核验实际 RSA assertion 的用途、缓存和 sender 的发送前授权检查。
未连接真实 Google、未配置厂商通道，也未修改 Android。
